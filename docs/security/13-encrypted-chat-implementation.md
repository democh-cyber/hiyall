# Encrypted direct chat: implementation record

**Status, 13 October 2026:** a working 1:1 chat (text, photos, reactions and replies), first run on an Android emulator on 8 October; safety numbers and FCM push (sender and app token registration) are built. Not run on a real device end to end. This follows [the library evaluation](12-e2ee-library-evaluation.md). It is not yet the independent integration review required before launch.

## Protocol use

- **Sessions:** Olm version 1 only. Inbound sessions with any other configuration are rejected, so there's no downgrade.
- **Key checks:** every peer Curve25519 key and pre-key base key is checked to be contributory, on top of vodozemac 0.11.1's own `NonContributoryKey` rejection. This covers the February 2026 report.
- **Signed statements:**
  - Each device signs `hiyall-device-v1\n{user}\n{device}\n{identityKey}\n{signingKey}`.
  - Each one-time key signs `hiyall-otk-v1\n{user}\n{device}\n{keyId}\n{key}`.
  - The server and the clients both verify these signatures. The clients don't rely on the server's check.
- **Device pinning:** device keys are pinned on first use. A known device id presenting different keys stops sending with `KEY_CHANGED`. A new device on a known account is announced (see [Hardening](#hardening-after-the-13-october-audit)). Safety numbers can be compared and marked verified.
- **Message payload:** each payload is JSON `{v, kind, text, messageId, conversationId, senderId, sentAt}`. The receiver rejects it unless these fields match the relay metadata, so the server can't replay ciphertext into another conversation or as another sender. The kinds are `text`, `image` ([attachments](14-encrypted-chat-attachments.md)) and `reaction` (see [Reactions and replies](#reactions-and-replies)); a text or image payload may also carry a quote, `re`. A kind this app does not know, sent by a newer app, is ignored: no bubble, no notice, no error.
- **Delivery:** each message carries one envelope per active device of the peer, plus the sender's other devices. The server rejects any other set with `DEVICES_CHANGED`, so devices can't be silently skipped or injected.
- **Ordering:** ratchet and account state are saved before ciphertext leaves the device. On receive the order is decrypt in memory, write the history, save account and sessions in one write, acknowledge (see Hardening). All Olm calls are serialized. This follows vodozemac's guidance against message-key reuse.
- **Server retention:** the server deletes ciphertext once a device acknowledges it. Blocking closes the conversation and deletes undelivered ciphertext in both directions. Revoking a device deletes its keys and pending ciphertext.

## Storage

- **App:** the pickle key, encrypted pickles, pinned keys and history are stored with `flutter_secure_storage` (Android Keystore / iOS Keychain backed, iOS items "after first unlock, this device only"). History is capped at 500 messages per conversation. Account and sessions are one entry (`hiyall.chat.<uid>.state`). Everything chat-related is erased on sign-out and account deletion, and on the first launch after a reinstall.
- **Web:** chat is unavailable and shows a notice. Browsers can't hold keys with keystore-grade protection.
- **Command-line peer:** `tool/chat_peer.dart` stores its state in `.runtime/chat-peer-<user>.json` (mode 600) for local testing only.

## Group chat

Groups of 3 to 10 people reuse everything above: each message is sealed once per recipient device with the existing Olm sessions (no group key, no sender-key ratchet; cost is O(devices of all members) per message), the relay adds a roster, roles and a name to what it already knows, and membership changes travel as encrypted control messages in the same request that changes the roster. What this adds to the independent review, in particular that the relay asserts additions to the roster and that removals are enforced by the phones, is in [group chat: experience and encryption design](../mobile/19-group-chat.md#security-notes-and-review-items); the server contract is [group chat API](../api/29-group-chat.md).

## Real-time delivery, receipts and verification

- **Gateway.** `GET /v1/realtime` upgrades to a WebSocket authenticated by the same bearer token (`internal/httpapi/realtime.go`). Events are wake-up signals only: `inbox`, `activity`, `read`, `typing`, `ready`, `resync`. They never carry message text or ciphertext. Clients fetch and decrypt over HTTP as before, so a lost event costs latency, never data.
- **Fan-out.** `internal/realtime` keeps per-node connections behind a `Bus` interface. Locally and in a single regional cell, `PGBus` uses PostgreSQL LISTEN/NOTIFY on a dedicated connection, with large audiences split under the 8 KB payload limit. Above that, a Redis or NATS bus with per-node routing replaces it without changing callers. After a bus reconnect, every client is told to `resync`.
- **Limits.** Each connection has a 64-event queue, and a client that falls behind is disconnected rather than buffered. There are 10 sockets per account and 100k per node; above that the client gets a 503 and falls back to polling. Heartbeats run every 25 seconds, the read limit is 4 KB, and typing is limited to 1 per 2 seconds per socket. Shutdown closes sockets so clients move to another node.
- **Client.** `RealtimeClient` reconnects with jittered exponential backoff (up to 30 seconds). `LiveSync` routes signals. While connected, the inbox poll is a 60-second safety net; without a socket it polls every 10 seconds (web, offline, gateway at capacity). The socket closes in the background and resyncs on resume. Web never opens a socket, because bearer tokens are not put in URLs.
- **Inbox at scale.** Migration 0008 adds `conversation_members`, one row per participant. Each row holds a sort key, a read pointer and an unread counter maintained on write. A conversation-list page is a single index range, and the unread badge is O(1). Inbox reads update `last_seen_at` at most every 5 minutes, and acknowledgements match on uuid so the primary key is used.
- **Read receipts and typing** follow the existing `readReceipts` privacy setting and are reciprocal: both people must have it on. Your own devices always learn that you read something, so badges clear everywhere. Read pointers use the relay's clock (`serverAt`), not the sender's.
- **Push.** `PUT/DELETE /v1/devices/{id}/push` stores an FCM or APNs token. A token is moved when it is reused and cleared when its device is revoked. The `push.Dispatcher` sends content-free wake-ups off the request path from a bounded queue, only to users with no socket on that node. `LogSender` stands in until FCM/APNs credentials exist.
- **Safety numbers.** The safety-number screen shows 60 digits derived from both accounts' current device identity keys, each checked against the keys pinned on first contact: 5200 rounds of SHA-512 per side, ordered by user id. Adding or removing a device changes the number. The screen never pins a device: a change is shown first, and a persisted "verified" mark per peer clears when either account's devices change.
- **Devices.** Profile → Chat devices lists the account's devices, with last activity shown only to the owner. Any device other than the current phone can be removed. The list and removal work without a started chat engine (they use only the account credential), so they are usable when registration fails with `TOO_MANY_DEVICES`.
- **Expiry.** An hourly sweep deletes delivered envelope rows after 7 days and undelivered ciphertext after 30 days, in batches of 5,000.

## Reactions and replies

Both live entirely inside the encrypted payload. The relay learns one new thing, a one-word hint on reactions (below), and never a target, an emoji or a quote. Engine: `core/chat/chat_engine.dart` (`parseIncoming`, `send(replyTo:)`, `react`), `chat_reactions.dart` (the allow-list, last-writer-wins state, the quote), `chat_history.dart` (storage and the waiting map). Server: `messages.aux` (migration `0032`), [API](../api/24-chat-reactions-and-replies.md).

### Wire format

A reaction (plaintext, before Olm). `to` is the reacted message's id, `op` is `add` or `remove` (a removal names the emoji being removed), `messageId` is this reaction's own id, which is also the relay's idempotency key:

```json
{"v":1,"kind":"reaction","text":"","to":"6d6d0000-0000-4000-8000-000000000002",
 "emoji":"\u2764\uFE0F","op":"add","messageId":"…","conversationId":"…","senderId":"…",
 "sentAt":"2026-10-13T10:00:00.000Z"}
```

A reply is an ordinary `text` or `image` payload with one more field. `snip` is the quoted message's own text (an image's caption, or empty) as one plain line, at most 120 code points; `k` is `text` or `image`; `by` is the quoted message's sender:

```json
{"v":1,"kind":"text","text":"see you there","messageId":"…","conversationId":"…","senderId":"…",
 "sentAt":"…","re":{"id":"6d6d0000-0000-4000-8000-000000000002","by":"<user id>",
 "snip":"8ish, cups are covered","k":"text"}}
```

The send request for a reaction adds `"aux":"reaction"` beside `messageId`, `senderDeviceId` and `envelopes`; no other message sets it.

### Validation on receive

- **Reaction:** the relay-metadata binding (`v`, `conversationId`, `senderId`, `messageId`, `text` is a string) is checked first and a mismatch is rejected like any other message. After that a reaction is **ignored, never rendered, never an error** unless `to` is a canonical lowercase UUID, `emoji` is exactly one of the six strings `❤️ 😂 👍 😮 😢 🔥` (byte for byte: `❤` without its variation selector, skin-toned or doubled emoji and everything else fail), `op` is `add` or `remove`, `sentAt` parses and is no more than ten minutes after the relay's own `createdAt` (so nobody can pin their own reaction in the future), and `messageId` is a UUID.
- **Quote:** `re` is read only if `id` and `by` are canonical lowercase UUIDs, `by` is one of the two members (when this device has only seen its own other device so far and does not know the peer yet, only the shape is checked), `snip` is plain text of at most 120 code points with no control, line-break or bidirectional-override characters, and `k` is `text` or `image`. Otherwise **the quote is dropped silently and the message shows without it.** Extra keys are ignored. A quote on a reaction is not read.
- **No nesting:** the sender's snippet is built from the quoted message's own text, never from its quote.
- **The quote is attributed text, not proof.** The receiver cannot check it against the original, and a sender can put any words in what they send, attributed to anyone in the chat; that is all a sender can already do by writing a message. When the original is in this device's history the **local** author, text and kind are shown instead of what the sender wrote (`resolveReply`, applied when the message arrives and again when it is drawn, so an original that arrives later still wins).
- **Unknown kinds and old apps.** A reaction is ignored by this app if it is invalid and by design never becomes an "unsupported" bubble. An older app that does not know the kind reads it as an empty text message (the payload keeps `text` as a string, as the binding requires): the relay's `aux` flag means it is not unread and not pushed, but such an app would draw an empty bubble. Nothing has shipped yet, so this is accepted.

### Ordering and storage

- **Last writer wins per sender per message**, by `(sentAt, then messageId)` of the reaction message. Each member's latest event is stored with the message, including a removal (a tombstone), so a late `add` cannot resurrect a removed reaction and two devices converge whatever order the envelopes arrive in. One reaction per member per message: a new `add` replaces the previous emoji, `remove` clears it. A reaction by the same account from another of its devices is applied the same way.
- **Waiting for the target.** The history is per conversation, so a reaction can only apply to a message of its own conversation. If the target is not in local history yet (the peer's and your other device's envelopes can arrive in either order) the event waits in a small map keyed by target id (at most 200 targets per conversation, oldest arrival evicted first, each dropped seven days after it arrived) and is applied when the target arrives. The map is stored beside the history, so a restart keeps it.
- **History JSON** gains two optional keys per message, `rx` (sender id to `{e, at, id}`) and `re` (the quote). History written before them loads unchanged; an entry this app did not write is skipped, not fatal. Reactions share the 500-message cap with their message.
- **A reaction is not a message:** it adds no row, never counts as unread locally, never changes the chat list preview, and is not offered as report evidence (the history has no row for it, and the server drops one from an evidence list if it is sent).
- **Sending.** `react` shows the reaction at once, sends it through the same `_deliver` as a message (one envelope per device, the relay's idempotency by message id, `DEVICES_CHANGED` retried once) with the `aux` hint, retries a transient failure twice with the same id (a retry cannot duplicate), and takes the reaction back and throws if it still fails. If a send fails after the relay stored it and every retry also fails, this device shows the old state while the peer sees the new one until the next reaction; there is no better answer without a confirmation round trip.

### The `aux` hint: what the relay learns, and why that is acceptable

The relay cannot read a message's kind, so it needs a hint to keep reactions out of unread counts, pushes and chat-list order. The hint is set by the sender, so it is a **metadata leak by design**: the relay (and anyone who can read its database or logs) can tell which messages are reactions, how many a pair exchanges and when. It cannot tell which message was reacted to, with what, or whether it was added or removed, and the envelope sizes of reactions and short texts overlap. Alternatives that avoid the leak (a reaction indistinguishable from a message) would make every reaction a push, an unread and a list reorder, which is worse for the people involved and for abuse (a reaction flood would be a notification flood).

- **A sender who lies gets nothing for it (re-audit CHAT-3).** `aux` on an ordinary message used to make it not count as unread and not push, and to skip the first-contact cap, so a stranger could send up to 2 KiB texts as "quiet" messages past the cap. Two changes close that, on both ends: the relay **counts aux messages toward the first-contact budget** like any other (below), and the receiver **drops any message the relay flagged `aux` whose decrypted kind is not `reaction` or `noop`**: no bubble, no notice, no unread, acknowledged (`parseIncoming(aux:)`; the inbox item carries `aux: true` for exactly this cross-check). So `aux` can no longer carry a message to anyone. What a stranger can still do is spend their own first-contact budget on envelopes the receiver discards, which stored ciphertext limits (below) bound.
- **Server rules for `aux` messages** (`SendMessage`): every existing gate applies unchanged (blocks, age band, `messagesFrom`, exact device set, idempotency: a replay of a stored message id is answered from the stored row, quietly if it was a reaction). Then, only for `aux`: no unread increment for the peer, no `last_message_at` or member `sort_at` update (a reaction never reorders the list), the sender's read pointer is left alone, no push, but the realtime `inbox` signal is sent so the peer fetches it at once. Each envelope is at most 2048 bytes decoded (`413 TOO_LARGE`), and at most 60 reactions per sender per conversation per ten minutes (a token bucket in the shared `ratelimit` package, burst 60, one token back every ten seconds, `429 RATE_LIMITED` with `Retry-After`; with `RATE_LIMIT_BACKEND=postgres` it is shared by every node). A reaction also spends a token of the ordinary per-account send limiter, so it can never be a way round it. Reactions are counted by the same limiters and the same daily quota as messages (below). A reaction by the peer is not "the peer replied": it does not unlock photos or `messagesFrom` for the other side, and it is not counted when the app decides whether a conversation has ever held a message.
- **Retention.** A reaction's envelopes expire exactly like a message's (delivered rows after 7 days, undelivered after 30, deleted on block or device revocation). The `messages` row keeps `aux = true`, so unread recounts, the "has the peer written" gates and report evidence can tell it from a conversation turn.

## Hardening after the 13 October audit

Findings C1 to C12, D1 and U1 of the v1 audit. Code: `core/chat/chat_engine.dart`, `chat_history.dart`, `chat_local_data.dart`, `chat_blob_cache.dart`, `chat_text.dart`, `features/chat.dart`; server `store/chat.go`, `httpapi/chat.go`, migration `0035_chat_devices.sql`. Tests: `test/chat_robustness_test.dart` (41, most over two devices with the real Olm core and the in-memory relay), `test/chat_robustness_ui_test.dart`, `internal/httpapi/chat_devices_test.go`.

### Sessions that cross, and unwedging (C1)

- Up to **5 Olm sessions per peer device**, newest first, persisted as a list per device. A pre-key message goes to the session whose id it carries (`matchesPreKey`); if it matches none, a new inbound session is created **and added**, never replacing one. Any other message is tried against each session in order. The session that last decrypted moves to the front and is the one used for sending, so two devices that both started a session (two people waving at once) converge after the first reply in each direction. A failed decrypt restores the session from its pickle, so a failure cannot damage a working one.
- A replayed pre-key message (also one that used the fallback key) matches the session it created, fails to decrypt (the message key is spent) and changes nothing.
- **Unwedge:** when a peer device's message cannot be decrypted, the device starts a fresh outbound session to it and sends an empty `noop` payload on it, flagged `aux` (quiet: not unread, not pushed, 2 KiB cap, same limiters as a reaction; the relay cannot tell it from a reaction, so it counts toward the first-contact budget until the peer has written, which is when an unwedge is ever needed), at most **once per hour per peer device** (persisted). The peer receives a pre-key message, adds a session and the two sides match again. `noop` is an ignored kind: no bubble, no notice. The failed message itself shows the usual "couldn't be decrypted" notice.
- Messages already in the history or opened in this run are acknowledged without decrypting again (a lost acknowledgement does not look like a decryption failure).

### Relay time orders everything (C4)

Messages are ordered, evicted (500 per conversation) and read-pointed by the relay's `serverAt`. `sentAt` is the sender's claim: the time shown is `sentAt` only within ±10 minutes of `serverAt`, otherwise `serverAt`. A burst of future-dated messages sorts where the relay received it and cannot push out older history or reorder a victim's own messages. Messages not yet accepted by the relay use the local clock.

### Sign-out, deletion and reinstall (C2)

- On sign-out and when the session ends for any reason, every `hiyall.chat.<uid>.*` secure-storage entry (the snapshot key, pickle key and device id), `chat_state` (the sealed snapshot), `chat_blobs` and `chat_outbox` are deleted (`ChatLocalData.wipeAccount`). The stored owner id (`hiyall.chatowner`) means a sign-out is cleaned up even if the chat engine was never built in that run. A signed-out state is only believed when the session provider has resolved (not while it is still loading).
- This phone's chat device is revoked on the server before the credential is dropped (a sign-out hook, 4 s timeout). If that fails the device id is kept under `hiyall.chatrevoke.<uid>` and removed on the next start of the same account. The server also revokes the device itself when its auth session is revoked (below).
- iOS items use `first_unlock_this_device`: no iCloud Keychain, no backup, no move to a new phone. The Keychain survives deleting the app, so a **marker file** in the app's support folder (which does not survive) tells a fresh install from a launch: marker absent and chat items present means they are erased, the old device ids are queued for removal, and a new identity is registered. Behaviour change: a build upgrade from before this change looks like a fresh install once.
- Android: `allowBackup=false` plus `dataExtractionRules` and `fullBackupContent` that exclude every domain.
- iOS backup exclusion (re-audit, other P3): `ios/Runner/AppDelegate.swift` answers a method channel (`app.hiyall/backup`, `excludeFromBackup`) by setting `isExcludedFromBackup` on `chat_state`, `chat_blobs` and `chat_outbox` (only paths inside the app support folder are accepted). `ChatBackupExclusion.apply` (`core/chat/chat_backup_exclusion.dart`) creates the folders and calls it before the engine opens the snapshot, on every engine build, because a sign-out wipe deletes the folders. **Needs a device or Xcode check**: the native handler is written but has not been built or run (no macOS build here); the Dart side is tested with a mocked channel.
- Shutdown before wipe (re-audit, other P3): `ChatEngine.dispose()` returns a future that completes when the work in flight (the serialized queue, photo preparation and uploads, writes already started) has finished, at most 5 s. From the first line of `dispose` the engine's store refuses writes (`GuardedChatStore`), the photo cache refuses `put` and `adopt`, the outbox refuses `enqueue` and `retry`, and the queue refuses new work, so nothing that was in flight can put a file or an entry back after the wipe. `ChatLocalData.wipeAccount` first stops and waits for the account's running engine (registered at start), whoever triggers the wipe, and the engine provider waits for the previous engine before it wipes. Tests: `test/chat_limits_test.dart` (a poll and a send in flight over a slow store and the real sealed snapshot, then a wipe: no entry and no file afterwards, and new work throws).

### Device lifecycle (C5)

- An inbox `404` (the relay no longer holds the device) first makes the app register the **same device id and keys** again (round 4, CHAT-N1): a device the relay removed only as idle comes back as itself, so nothing is replaced and no one is told a device was added (see "Fourth audit" below). A registration refused with `409 DEVICE_CONFLICT` (removed by someone, or keys that belong to something else) makes the app discard this device's identity (state, account, sessions, id, pickle key, and the verification marks) and register a new one, **keeping every pin**: other people's devices and this account's other devices (only this device's own pin goes). History stays. The person is told (a `reset` notice, below). The old device id is queued for removal on the relay. `TOO_MANY_DEVICES` is not reset: the person removes a device.
- **An account that cannot be unlocked (re-audit CHAT-5).** If the saved account cannot be opened (the pickle key is missing or different, or the `state` entry is damaged) the engine used to stop for good. It now runs the same reset on its own and raises a `locked` notice, "Couldn’t unlock your encrypted data on this device. Starting fresh.": the Olm account and sessions are gone, so earlier encrypted messages cannot be opened here. A storage read that fails (a keystore that is not ready) is not this case: it is an error to retry, nothing is thrown away (see the next entry). **The same notice is raised when the snapshot is lost or rolled back (round 3, CHAT-N8):** snapshot files that existed and none opened (the key is gone: a wiped keystore with files left behind, or damaged files) is `SnapshotOpenInfo.lost`, and a snapshot that could only be opened from `.snap.prev` (the current file and any newer one were unusable, so the saved ratchets may be older than what peers already saw) is `SnapshotOpenInfo.rolledBack`; either way the engine resets the identity before it loads anything (`locked` notice, the old device queued for removal) instead of carrying on with it, or starting empty without saying so. Tests: `test/chat_round3_test.dart`. The reset deletes `state` first and the pickle key last, so a kill between two steps leaves a key with nothing to open (a new account is made under it) and never state without its key. Tests: `test/chat_limits_test.dart` (missing key, damaged entry, a keystore that fails once, the deletion order, a kill at every delete and at every file step of the real sealed snapshot, each followed by a restart that chats normally).
- **A keystore that cannot be read never regenerates anything (round 3, CHAT-N4).** The Android plugin's default is to erase everything it holds on any read error, after which the engine made a new key and started with no history and a new identity. Every `FlutterSecureStorage` in the app is now made by one factory (`lib/core/secure_storage.dart`, `createSecureStorage`) with `AndroidOptions(resetOnError: false)`; the chat store keeps its iOS Keychain accessibility (`first_unlock_this_device`) and every other store its default. `SecureChatStore` turns any platform failure into `ChatStorageUnavailable`; reading the snapshot key or the pickle key then fails the start instead of making a key (only an absent entry makes one). The app shows "Couldn’t open secure storage. Nothing was deleted." and opens the engine again after 3, 10, 30, 60 and 120 seconds. The launch is counted once in a small plain file in the app folder (`chat_storage_health`, a number and a time); after **3 launches in a row** the screen also offers **"Reset chat on this phone"**, which asks first in plain words and then erases this account's snapshot, photos and keys (single entries first; when the keystore cannot list them, this account's chat entries by name, `ChatLocalData.eraseKnownEntries`; since round 4 nothing else the app keeps in the keystore is touched, CHAT-N7), makes a new identity and shows the `storage` notice. The old device stays on the account's list until it is removed in Chat devices or goes idle (35 days). Tests: `test/chat_round3_test.dart` (an engine whose keystore fails deletes and regenerates nothing and later opens as the same device; the counter; the reset), `test/chat_devices_ui_test.dart`.
- Maintenance revokes devices unseen for **35 days** (`stale chat devices`, 500 per hour; it was 90, then 14 in round 3, and is 35 since round 4, CHAT-N1: longer than the 30-day ciphertext expiry), as **idle** (`revoked_reason = 'idle'`, `revoked_by_other`, migration `0045`): the push token and unclaimed keys go, which frees the 10-device cap, and ciphertext that has not expired is kept. The same app registers again with the same keys and the row is active again. A second hourly job, `backlogged chat devices`, revokes a device that holds **more than half the backlog cap (over 1000 undelivered envelopes) and has not polled for 3 days** (`Store.RevokeBackloggedDevices`).
- **A dormant device cannot block its owner's inbound chat (round 3, CHAT-N1).** The 2000-envelope cap (below) trips after about 67 messages a day over 30 days, and a reinstall on Android leaves the old device behind: every peer then got `429 RECIPIENT_BACKLOG`. Now a send that finds a device over the cap whose `last_seen_at` (touched by its inbox poll every 5 minutes) is **more than 7 days old** revokes that device **inside the send's transaction** (keys and ciphertext dropped, `revoked_by_other = true`, `revoked_reason = 'inactive'`, migration `0042`), commits the revocation and answers `409 DEVICES_CHANGED`; the client already refetches the device list and retries once, so the message goes through to the devices that remain. A device that polled in the last 7 days is a slow device, not a dormant one, and is never revoked here (it gets the 429). The revoke is an `UPDATE … WHERE last_seen_at < now() - 7 days`, so a device that polled meanwhile is left alone, and sends that touch the same account are serialized by `lockPair`, so concurrent senders revoke it once and every one of them is told `DEVICES_CHANGED`. The owner's other devices get the `device-revoked` realtime signal (`reason: "inactive"`) and push, except the phone that was mid-send; the removal is listed in `removed` with `reason: "inactive"` and the app shows "A device you hadn’t used for a while was removed" (`DeviceNoticeKind.inactive`). Tests: `internal/httpapi/chat_devices2_test.go` (`TestDormantDeviceOverTheCapIsRevokedInTheSendAndTheTrafficSelfHeals`, `TestADormantOwnDeviceOverTheCapIsRevokedWhenTheSenderSends`, `TestConcurrentSendsToADormantFullDeviceRevokeItOnceAndNobodyFails`, `TestBackloggedIdleDevicesAreSweptAndActiveOnesAreNot`).
- Migration `0035`: `devices.session_id` (the auth session that registered, or last registered, the device) and a trigger on `sessions.revoked_at`: revoking a session revokes its devices, their keys and pending ciphertext, however the session was revoked (sign out, sign out everywhere else, suspension, deletion).

### New devices are announced (C3, interim)

There is **no cross-signing**: anyone who can authenticate to the account can register a device, and from then on receives the account's new messages (not older ones). What exists instead:

- The relay sends a `device` realtime event to all of the account's devices on registration and removal. Each other device re-reads its list and shows an in-app banner with a link to Chat devices and a dismiss (persisted until dismissed). A content-free **push** goes to the account's other devices (below).
- **What the banner can say** (`DeviceNotice.kind`, `deviceBannerText`): `added` "A new device was added to your account"; `review` "Review your devices"; `removed` "A device was removed from your account"; `reset` "This phone started a new secure chat identity"; `locked` "Couldn’t unlock your encrypted data on this device. Starting fresh."; `storage` "Chat was reset on this phone" (the explicit reset, below); `inactive` "A device you hadn’t used for a while was removed". The most pressing wins; all stay until dismissed, across restarts.
- **Nothing is pinned silently (re-audit CHAT-2).** A phone that knows none of the account's devices (a fresh install, a sign-in after a wipe, a reset that left no pins) and finds others on the relay pins them, because it must in order to send, and raises one `review` notice. The first device of an account has nothing to review. A phone that kept its pins announces each device that appeared since as `added`. This closes the bypass where revoking the owner's phone and letting it reset used to erase the pins and the notices, so the thief's device was pinned as if it had always been there.
- **A removal is recorded and fetched.** `DELETE /v1/devices/{id}` from a session other than the one the device registered under (another phone, or a stolen credential) sets `devices.revoked_by_other` (migration `0040`). `GET /v1/me/devices` returns those, for 30 days, as `removed: [{deviceId, removedAt, reason?}]`; a device that had pinned one raises a `removed` notice (or `inactive` when `reason` is `"inactive"`, a device the relay removed for being dormant) and drops the pin; the pin and the notice are written in **one** snapshot commit (CHAT-N6). The device's own sign-out and a session revocation do not set it; the dormant revocation and the backlog sweep do, with `reason: "inactive"` (migration `0042`), and the 35-day idle sweep and the in-send idle removal do, with `reason: "idle"` (migration `0045`; the device may register again with the same keys). The realtime `device` signal carries `by: "self"|"other"`, but nothing depends on receiving it.
- **The list is looked at again** on the socket's `ready` and `resync`, on every app resume, and on a `device` signal (the periodic syncs throttle it to once per 25 s): a signal that was missed no longer hides a device. Server: `Store.RemovedDevices`; app: `refreshOwnDevices`, `LiveSync.syncAll`.
- Push `device` and `device-revoked` (kind `device-revoked` when another session removed a device, sent to the remaining devices): the fixed texts "New device added to your account" and "A device was removed from your account", data `{kind: device}` and nothing else, no device name. They belong to the category `security`, which the member's chat and social choices cannot switch off, and, unlike chat, they **ignore a live socket** (whoever holds a stolen token can keep one open for the account) and have **no coalescing window**; they have **their own cap of 20 per recipient per rolling 24 hours**, counted apart from the 200 that chat and social share. The other rules still hold (active account). **The device that performed the removal is left out of the push (CHAT-N7):** the relay finds it as the active device registered under the removing session and passes its id as the notice's excluded device, so the phone that tapped "remove" is not told about what it just did. Tapping it opens Chat devices (`/profile/devices`). Server: `internal/push/push.go`, `httpapi/chat.go`, `store/push.go` (`PushAudience`); app: `PushTap.device`. Tests: `internal/push` (`TestSecurityPushesIgnoreALiveSocketTheChatCapAndTheWindow`, `...HaveTheirOwnSmallDailyCap`, `TestDeviceRevokedPushIsContentFree`), `internal/httpapi/chat_limits_test.go` (`TestStolenTokenCannotSilenceTheDevicePushes`: a stolen token holds a socket open, registers a device and removes the owner's phone; `TestRevokingAnotherSessionsDeviceIsRecordedForTheOwner`), `test/chat_limits_test.dart` and `test/chat_devices_ui_test.dart` (the notices over the real Olm core, the resets, the refresh on ready, resync and resume).
- A peer's new device is recorded per peer and shown as a notice in **every** conversation with that person the next time it is opened, and at once in the conversation that saw it.
- The safety-number screen reads the relay's current lists without pinning. It shows a change first ("changed since you verified", "added a device since your last message"). A `verified` mark is stored per peer with fingerprints of both accounts' device sets and clears when either changes; the header menu shows its state.
- The privacy policy and data-retention text (`docs/legal`, `assets/legal`, identical) describe this caveat.

### Text outbox (C9)

A text is written to the history as "sending" with its final id before any network call. A transient failure (offline, 429, 5xx, 401) leaves it "not sent" with Retry and Delete under the bubble; a restart shows an interrupted send the same way; retry rebuilds the identical payload with the same id, which the relay answers idempotently. A refusal (not allowed, closed, a changed key, `AWAITING_REPLY`) removes it and puts the text back in the composer.

### Atomic encrypted storage and the receive path (C8)

Everything the engine keeps for an account, except three small secrets, is one sealed file: `<app support>/chat_state/<userId>.snap` (`core/chat/chat_snapshot.dart`, `SnapshotChatStore`). It holds the Olm account and sessions (`state`), pinned device keys, the "new device" and verification notes, every conversation's history, waiting reactions and the photo outbox index. The three secrets stay in the platform keystore (this device only): the **snapshot key** (32 random bytes made by the Rust core, `generate_seal_key`), the Olm pickle key and the device id. Sign-out and reinstall handling read them without opening the snapshot.

- **Format.** `HYCS | version 1 | generation (u64) | nonce (24) | ciphertext | tag`. XChaCha20-Poly1305 (`api/seal.rs` over the same `chacha20poly1305` crate as the attachments, no new dependency), a fresh random nonce per write, and the account id plus the generation as authenticated data: a snapshot cannot be moved to another account or have its generation changed. The plain content is length-prefixed key/value records (UTF-8), so large histories are not escaped twice. The Olm pickles inside are still encrypted with the pickle key.
- **Commit.** Write `<id>.snap.tmp`, `fsync` it, rename `.snap` to `.snap.prev`, rename `.tmp` over `.snap`. Whatever step a crash stops at, a file that opens is either the old snapshot or the new one (every file is whole or fails authentication). On open the newest generation that decrypts among `.snap`, `.tmp` and `.prev` wins, so a half-written temporary file is ignored and a damaged main file falls back to the spare. A crash after the new file is on disk but before the call returned leaves the new state; the message that caused it was not acknowledged, comes back, and the history recognises it. The folder itself is not fsynced (Dart cannot); rename durability relies on the file system.
- **Coalescing.** Writes apply in memory at once and every write that arrives while a commit runs joins the next one; a write returns when its commit is on disk, or throws and puts its entries back as they were. Writing a value that is already there does nothing. `ChatStore.batch` makes everything its work writes one commit, all or nothing, and holds back other writers until it ends (nested calls just run). `ChatHistory.transaction` takes the history lock first (the same order everywhere, so the two locks cannot deadlock) and, if the transaction fails, drops its cached lists so the next read shows what disk holds.
- **Receive path.** Per message: decrypt in memory; then **one commit** of the history row (or the reaction), waiting reactions and the account and sessions (`ChatHistory.transaction(ingest + saveState)`); then acknowledge. A failed commit rolls the in-memory ratchet back (`undo`) and leaves the message on the relay. A crash at any disk step leaves ratchet and history both old or both new and the message arriving exactly once (`test/chat_snapshot_test.dart`: the whole poll is crashed at every step with the real Olm core). Account and sessions can no longer be ahead of the history or the reverse.
- **Migration.** First open with entries written by earlier builds (one secure-storage item per key): they are read, written into the snapshot (generation 1), and only then deleted. A crash before the snapshot is written leaves the old items; after it, the snapshot wins and any left-over old items are deleted on the next open. The keystore items `pickleKey`, `deviceId` and `snapKey`, other accounts' items, the owner marker and the pending-revoke note are never touched.
- **When the snapshot cannot be opened** (the keystore item is gone, the files are damaged and the spare too): the files are deleted, the account starts empty and registers a new device (the relay answers `DEVICE_CONFLICT` for the old id, which makes the app start over and tell the person, a `reset` notice). History and sessions are lost.
- **Wipe.** `chat_state` is in the folders sign-out and reinstall handling delete.
- **Remaining.** A device that is rooted or whose backup contains both the keystore item and the folder can read the snapshot; the keys are this-device-only on iOS and excluded from backup on Android. Nothing stops an attacker who can write the folder from putting back an older snapshot (no monotonic counter); that rolls the ratchet back on that one device only. The ciphertext photo cache (`chat_blobs`) and unsent uploads (`chat_outbox`) are separate files and not part of the snapshot (they are not ratchet state). Whole-file rewrite on every commit costs a few ms per message for 500-message histories; a database would avoid it and is not needed at this size.

### Fallback key rotation (F11)

The fallback key is what a peer uses when every one-time key of a device is claimed. The engine replaces it every **7 days** (checked after each fully read inbox page, so a device that is open or woken by a push does it) and **forgets the previous one 24 hours after the new one reached the relay** (`forget_old_fallback_key` in `rust/src/api/e2ee.rs`, vodozemac's `forget_fallback_key`, exposed through the regenerated flutter_rust_bridge binding). The rotation time is only recorded once the upload succeeded (the old key keeps working until then; a fallback key made by an attempt that did not reach the relay is offered again instead of pushing the published one out). The fallback key travels with the first key request, so a failing one-time-key upload no longer holds the rotation back (re-audit CHAT-1, below). Forgetting waits until the inbox has been read to the end with nothing left on the relay, so a pre-key message made for the old key that was waiting while the phone was off is opened first. After the key is forgotten a replayed pre-key message for it can no longer create a session. Both times are kept inside `state`, in the same snapshot commit as the account. Tests: `rust` (`forgotten_fallback_key_cannot_start_a_session`), `test/chat_hardening_test.dart` (rotation, restart, grace period, forgotten after it, not before the inbox is drained).

### Text padding (F16)

A text payload is padded, **inside the encryption**, to a size bucket of 64, 128, 256, 512, 1024, 2048 or 4096 bytes (UTF-8 JSON), then to a multiple of 1 KiB up to 12 KiB; bigger payloads are not padded (the envelope cap is 16 KiB). The filler is a `pad` string of random base64url characters (it does not compress). A receiver ignores `pad` but checks it is a string of at most 16 384 characters; a payload without one (older builds) parses as before. Reactions and the quiet "noop" are not padded (their envelopes are small and already marked `aux`), and photo payloads carry blob ids the relay already sees. The payload carries about 200 bytes of metadata, so in practice the smallest bucket a text lands in is 256 bytes; the relay learns the size class, not the length. `core/chat/chat_padding.dart`.

### Text rules in the app (S9)

The API's text rules (`internal/domain/text.go`: no Cc, Cf except ZWJ and ZWNJ between two visible characters, no Co, no line or paragraph separators, at most five combining marks in a row, NFC) cannot see a chat message, so the app applies the same rules itself (`core/chat/chat_text.dart`, with generated Unicode tables in `chat_unicode_tables.dart` from the same Go sources, `tool/chat_unicode_gen`). **Outgoing** text, photo captions and quote snippets are normalised to NFC and cleaned (what breaks the rules is removed); a message with nothing left throws `INVALID_TEXT`. **Received** text, captions and snippets are cleaned on receipt and again when drawn, never rejected. Both sides test against `services/api/internal/domain/testdata/text_vectors.json` (Go: `text_vectors_test.go`; Dart: `test/chat_text_test.dart`; regenerate with `UPDATE_TEXT_VECTORS=1`): `clean` and `nfc` must agree for every vector, including 400 seeded random sequences. One deliberate difference: the England, Scotland and Wales flags (a waving black flag, tag letters and a cancel tag) are emoji people send, so received and outgoing cleaning keeps a well-formed tag sequence and removes every other tag character; `isCleanText` itself stays as strict as the API (the vectors mark these cases `appKeeps`). Behaviour change: the soft hyphen, line and paragraph separators and joiners that are not between two visible characters are now removed from received text too.

### API client, background and lists

Every chat request carries `X-Client-Version` and `X-Client-Platform`; a `426 UPGRADE_REQUIRED` raises the same blocking "Update Hiyall" screen as the main client (`ChatApi.onUpgradeRequired` sets `upgradeRequiredProvider`). The engine's inbox timer stops while the app is in the background and restarts, with an immediate poll, when it returns (`ChatEngine.pause` and `resume`, driven by an `AppLifecycleListener`, like the other timers in LiveSync). The chat list builds only the rows on screen.

### Smaller server rules (G5, F21, F24)

- Device display names are the owner's alone: `GET /v1/users/{id}/devices` returns `displayName: ""` to anyone else (keys and signatures are unchanged); the owner's lists show the name.
- A push token is never taken from a live device of another account: `PUT /v1/devices/{id}/push` with a token another account's device holds answers `409 PUSH_TOKEN_IN_USE` (logged without the token or the other account, the response names nobody); moving a token between the same account's devices still works. **Exception (re-audit, other P3):** a token is a secret of one install, so presenting it shows this is that install; when the holder is a device of another account that has not been seen for 24 hours (`Store.StalePushHolderAfter`; a phone in use touches `last_seen_at` every five minutes), it is what a previous sign-in on this phone left behind (an offline sign-out, a reinstall). That device is revoked (its keys and undelivered ciphertext dropped, like any revocation) and the token goes to the caller. A holder seen within the day still refuses. The server cannot see "after a fresh login"; the token itself is the proof. Test: `TestPushTokenOfAStaleDeviceOfAnotherAccountIsHandedOver`.
- F24 was checked and is not a defect: the "has the peer written" check in `canMessage` already ignores auxiliary messages (`NOT m.aux`), so a peer who only reacted does not let the other side past a restricted `messagesFrom`. A regression test pins it (`TestAPeerWhoOnlyReactedDoesNotUnlockLookups`).

### Photos (C10)

A received descriptor may claim at most 2048 px on the long edge and 4 Mi pixels for the full image (the sender's own limits; a 2048 x 2048 square is allowed), 320 px for the thumbnail, a caption of 500 code points. Cached ciphertext is stored under a digest of conversation id, blob id and the descriptor's ciphertext hash, so a descriptor cannot point at another chat's photo or other bytes; a cached file that matches its own descriptor is never deleted because of a message, and dropping a message from the history deletes its cache entries only when no kept message names them. See [attachments](14-encrypted-chat-attachments.md).

### Relay rules (D1, U1, C12)

- The send path updates only the two `conversation_members` rows by primary key.
- **First-contact cap:** a sender may send `FirstContactMessages` = **3** messages in a conversation until the peer has sent a non-aux one of their own; the fourth is refused with `403 AWAITING_REPLY`. **Reactions and `noop` count too** (re-audit CHAT-3): the relay cannot read kinds, so exempting messages marked `aux` was a way round the cap. A peer's reaction is not a reply. Reactions and the noop are only meaningful once the peer has written, when the cap no longer applies; the one visible effect is that a reaction to your own message before the peer has replied can be refused. A replay of a stored message is not re-counted. The check is "is there a message of the peer's" (one index probe, `messages_conversation_sender`) and then a count that stops at the cap, so nothing scans a conversation under the row locks. The app shows "Waiting for <name> to reply" in the composer and disables it; Say hi counts as one of the three.
- **Stored ciphertext is bounded (re-audit CHAT-4).** Two throwaway accounts could store gigabytes for the 30 days an undelivered envelope lives. Now: (1) **no device holds more than 2000 undelivered envelopes** (`Entitlements.ChatBacklogPerDevice`); a send that would put any recipient device over (the peer's, or your own other devices') is refused `429 RECIPIENT_BACKLOG` with `Retry-After: 60`, the check running inside the send transaction after `lockPair`, which already holds the rows of both accounts, so every send that can add an envelope for those devices is serialized and the cap is exact under concurrency; the count walks `envelopes_inbox` and stops at the cap. A device that drains (acknowledges) frees room at once. (2) **At most 2000 messages per sender per conversation per rolling 24 hours** (`Entitlements.ChatMessagesPerConversationPerDay`, reactions included, never refunded), `429 CHAT_DAILY_LIMIT` with `Retry-After` until the oldest ages out; the count reads the last 24 hours of the conversation through `messages_conversation`. A replay of a stored message id is answered before either check. Both limits live in `domain.Entitlements`, so a later plan can change them. **Round 3 (CHAT-N2, N3):** the full device being the sender's own is answered `429 OWN_BACKLOG` (words: open Hiyall on that device or remove it in Chat devices; the app offers a button to Chat devices); the peer's stays `RECIPIENT_BACKLOG` with the same words. Besides the 2000, **no one sender may have more than 300 undelivered envelopes on one recipient device** (`Entitlements.ChatBacklogPerSenderPerDevice`, `RECIPIENT_BACKLOG`, `Retry-After: 60`; the sender's own other devices are exempt), so one account cannot fill a victim's device alone; and envelopes of a sender barred from the device's owner never count (the inbox does not deliver them). Tests: `internal/httpapi/chat_devices2_test.go` (`TestOneSenderCannotFillAVictimsDeviceAlone`, `TestEnvelopesOfBarredSendersDoNotCountTowardTheCap`, `TestOwnDeviceBacklogHasItsOwnCodeAndTheRecipientTextIsUnchanged`). Tests: `internal/httpapi/chat_limits_test.go` (boundary, refusal storing nothing, drain frees room, own-device backlog, six accounts sending to one recipient concurrently under `-race` with exactly the cap accepted, the daily boundary and its window, reactions counting, per-sender and per-conversation).
- **Key upload in chunks (re-audit CHAT-1).** Before, the core returned every unpublished one-time key, so after one failed upload the retry carried 80 keys against the relay's limit of 50 and `start()` failed on every launch. (Round 3, CHAT-N5 and N9: a failed upload no longer fails `start()` at all, see the third audit table; and a set of more than 50 unpublished keys left by an older build is uploaded whole, in chunks of 50, before the core marks any published: `chat_key_upload.dart`.) Now the core makes only the shortfall (`generate_one_time_keys(count)` ensures `count`, at most 50, are pending and never adds to them; a Rust test pins that repeated calls without publishing stay bounded) and the engine uploads in chunks of at most 50, one generate-upload-publish cycle each: the pending keys after any failure are those of the one chunk that did not arrive, and the retry sends exactly them. The relay is topped up to 60 when it holds fewer than 20; the fallback key rides with the first request. Tests: `rust` (`unpublished_one_time_keys_stay_bounded`), `test/chat_limits_test.dart` (offline on the first run then a restart from the saved account; three refusals in a row; the second chunk failing; fallback rotation after failures; a depleted relay topped up in two requests; the relay double of `test/chat_reactions_engine_test.dart` now merges and refuses over 50 per request and 100 held, as the server does).
- Per-account limiters (shared with the Postgres backend): device register, list and revoke (burst 20, one per 2 s), key count and upload (burst 30, 2/s), inbox and ack (burst 60, 5/s). Registered as `chat_devices`, `chat_keys`, `chat_inbox`.

### Rendering (F23)

Bidirectional controls, zero-width characters (except the joiners emoji need) and C0/C1 controls are removed from received text on receipt and again when a bubble is drawn. One unreadable history entry is skipped; an unreadable list is an empty conversation, not a crash.

The hourly sweep over 50,000 idle devices took 51 ms and 100.8k buffers (a probe per device) and takes 12 ms and 14k buffers (one barred-only candidate); the first run after a large backlog (50 candidates, all revoked) now takes 138 ms and 468k buffers because every candidate is counted exactly.

## On-device translation and reading aloud (Wave 7)

Chat is end-to-end encrypted, so every language feature runs on the phone. **No plaintext reaches a server or a third party**: not for translation, not for language detection, not for text-to-speech, not for search.

- **Translation** uses Google ML Kit's on-device translation (`google_mlkit_translation`, MIT; the models run locally) behind `TranslationService` (`lib/core/translate/translation_service.dart`), with `FakeTranslationService` for tests and for the story and comment translation that will reuse it. The only network traffic is the one-time download of a language pack (about 30 MB per language, English is built in; ML Kit pivots through English, so a pair needs both packs). The download carries no text. A pack is never fetched by surprise: the first translation shows a consent sheet that names the packs and the size and says the words stay on the phone, with a Wi-Fi-only switch; declining translates nothing. Packs are listed and deleted in Settings, Chat language.
- **Language detection** uses ML Kit language identification (`google_mlkit_language_id`, MIT), also local.
- **Translate to**: the person's choice, else the phone's language when a model exists, else English. Kept in the sealed local store.
- **Auto-translate** is a per-chat switch kept **only on this phone** (`ChatPrefs`, key `prefs` inside the sealed snapshot, so sign-out wipes it). It is never sent to the relay or the peer. It translates incoming text only when the packs are already installed (it never downloads by itself) and at most the newest 30 messages.
- **Where translations live: memory only.** A translation is a second copy of a message's text. Storing it anywhere outside the sealed snapshot would put message content in a new place, and storing it inside would grow every history write, so translations are held only in memory (`TranslationMemory`, bounded, cleared when the account's engine changes) and made again on demand. Closing the app forgets them.
- **Reading aloud** uses the platform engine through `flutter_tts` (MIT): Android TextToSpeech, iOS AVSpeechSynthesizer. Only a voice that works without the network is used (`pickOfflineVoice` skips Android voices flagged `network_required`); if none is installed for that language the person is told to install one in the phone's own settings. The text is spoken in the language detected (or the translation's language).
- **Search** of the chat list reads the decrypted local history only (`ChatEngine.searchHistory`), never asks the relay, and skips voice messages and videos.
- **Sentence correction** (grammar fixing by an online model, as other language-exchange apps offer) is **not built**: it needs a cloud model, which would have to receive the plaintext of a private message. An on-device correction model is not available with acceptable quality and size; revisit only if one appears.
- Not run on a device: ML Kit, the text-to-speech engine and the downloads need a phone (the iOS Simulator on Apple Silicon is not supported by ML Kit).

## Chat list: pins, deleted chats, local history (Wave 7)

Pins, deletion and restore are flags on the caller's own member row ([API 26](../api/26-chat-voice-video-and-list.md)); the peer learns nothing. "Delete chat" hides it; this phone's history is kept for the 30 days it can be restored; a new message from the peer, or opening the chat, brings it back. After 30 days the relay closes it for that member (hourly job) and the app wipes its local history (`ChatEngine.hiddenConversations` wipes the ids the relay reports closed, and any listed chat whose window has passed on the phone's clock). "Clear history on this phone" (`ChatEngine.clearHistory`) removes the messages, the waiting reactions, the cached files and any unsent upload of one chat locally and changes nothing for the peer. Read receipts ("Seen" / "Not read yet" under the newest sent message) are drawn only when the relay sends the peer's read time, which it does only when both people have read receipts on; with either off nothing is claimed.
