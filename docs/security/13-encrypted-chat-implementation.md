# Encrypted direct chat: implementation record

**Status:** integration proof plus a working 1:1 chat on Android, 8 October 2026. This follows [the library evaluation](12-e2ee-library-evaluation.md). It is not yet the independent integration review required before launch.

## What runs where

| Piece | Location | Responsibility |
|---|---|---|
| Rust core `kairova_e2ee` | `apps/mobile/rust/src/api/e2ee.rs` | Thin wrapper over vodozemac 0.11.1 (Apache-2.0): accounts, Olm sessions, encrypted pickles, strict Ed25519 checks. No custom cryptography. |
| Dart binding | `apps/mobile/lib/src/rust/` (generated by flutter_rust_bridge 2.13.0, MIT/Apache) | Our own binding, so the AGPL `flutter_vodozemac` isn't used. |
| Chat engine | `apps/mobile/lib/core/chat/` | Devices, key publishing, trust-on-first-use pinning, sessions, send/receive, local history. Pure Dart. |
| App UI | `apps/mobile/lib/features/chat.dart` | Chats list, conversation, Message button on profiles. Android and iOS only. |
| Relay | `services/api/internal/{store,httpapi}/chat.go`, migration `0007_chat_e2ee.sql` | Device public keys, one-time keys, conversations, per-device ciphertext. Never plaintext. |

## Protocol use

- **Sessions:** Olm version 1 only. Inbound sessions with any other configuration are rejected, so there's no downgrade.
- **Key checks:** every peer Curve25519 key and pre-key base key is checked to be contributory, on top of vodozemac 0.11.1's own `NonContributoryKey` rejection. This covers the February 2026 report.
- **Signed statements:**
  - Each device signs `kairova-device-v1\n{user}\n{device}\n{identityKey}\n{signingKey}`.
  - Each one-time key signs `kairova-otk-v1\n{user}\n{device}\n{keyId}\n{key}`.
  - The server and the clients both verify these signatures. The clients don't rely on the server's check.
- **Device pinning:** device keys are pinned on first use. A known device id presenting different keys stops sending with `KEY_CHANGED`. A new device on a known account adds a notice in the conversation. Safety-number comparison isn't built yet.
- **Message payload:** each payload is JSON `{v, kind, text, messageId, conversationId, senderId, sentAt}`. The receiver rejects it unless these fields match the relay metadata, so the server can't replay ciphertext into another conversation or as another sender.
- **Delivery:** each message carries one envelope per active device of the peer, plus the sender's other devices. The server rejects any other set with `DEVICES_CHANGED`, so devices can't be silently skipped or injected.
- **Ordering:** ratchet and account state are saved before ciphertext leaves the device and before a delivery is acknowledged. All Olm calls are serialized. This follows vodozemac's guidance against message-key reuse.
- **Server retention:** the server deletes ciphertext once a device acknowledges it. Blocking closes the conversation and deletes undelivered ciphertext in both directions. Revoking a device deletes its keys and pending ciphertext.

## Storage

- **App:** the pickle key, encrypted pickles, pinned keys and history are stored with `flutter_secure_storage` (Android Keystore / iOS Keychain backed). History is capped at 500 messages per conversation.
- **Web:** chat is unavailable and shows a notice. Browsers can't hold keys with keystore-grade protection.
- **Command-line peer:** `tool/chat_peer.dart` stores its state in `.runtime/chat-peer-<user>.json` (mode 600) for local testing only.

## Verified

- **Rust:** `cargo test` in `apps/mobile/rust`, 6 tests: round trip and ratchet, one-time-key consumption, replay of single-use keys, tampering, wrong identity, low-order keys, pickle keys, strict signatures.
- **Go:** chat integration tests, 3 tests, run with the race detector:
  - signatures and conflicts, the 10-device cap, the 100-key cap
  - one-time keys handed out exactly once, then the fallback key
  - `messagesFrom` gating and reply-after-contact
  - exact device sets, idempotent sends, message ids that can't be reused
  - per-device routing, inbox ownership, ciphertext deleted on ack
  - revocation, blocks, input validation, rate limits
- **Live:** `test/chat_live_test.dart` runs three real clients against the API: Anjali's phone and laptop, and Niko. It covers both directions, a 10-message burst, a restart from stored state, and pickles that don't expose keys. **Every request and response is captured, and none of the message text appears.**
- **Android emulator:** Anjali on the real app and Niko on the command-line peer exchanged messages in both directions. A full `pg_dump` of the dev database has no message text, and every delivered envelope's ciphertext is deleted.

## Not done yet (before launch)

- Independent review of this integration: key storage, device lists, envelope handling.
- Real-time delivery: currently polls every 2 seconds. WebSocket or push comes later.
- Safety numbers or a device-verification UI. Multi-device history sync for new devices.
- Attachments, reactions, edits, read receipts, message requests from non-allowed senders, and group chat (Megolm or MLS).
- iOS build and test (needs macOS). Proxy-certificate rejection tests and release artifact scans.
- Undelivered-ciphertext expiry (planned: 30 days).
