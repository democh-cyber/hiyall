# Group chat: experience and encryption design

Groups of 3 to 10 people, end-to-end encrypted, built on the one-to-one engine. Server contract, limits and errors: [group chat API](../api/29-group-chat.md). The encryption this builds on: [encrypted chat implementation](../security/13-encrypted-chat-implementation.md) and [encrypted attachments](../security/14-encrypted-chat-attachments.md). **Not run on real devices.** Like the rest of chat it still needs the independent crypto review before launch; the items this feature adds to that review are in [Security notes](#security-notes-and-review-items).

## How a group message is sent

There is no group key and no sender-key ratchet. A message to a group of N people is sealed **once per recipient device** with the Olm session the sender already has (or starts) with that device, exactly like a one-to-one message to someone with several phones:

1. The app asks the relay for the group (`GET /v1/groups/{id}`, cached for 30 seconds and refreshed by a realtime `inbox` signal or a `409 DEVICES_CHANGED`): the active members the sender can see.
2. For every member except the ones this phone has a removal for (see [Membership changes](#membership-changes)), it fetches and checks the member's devices like a one-to-one peer (signatures, contributory keys, pins on first use, the "new device" notice) and starts an Olm session to any device it has none with.
3. It seals the identical payload for each device (and for the sender's other devices) and posts them in one request. The relay accepts the request only when the set of devices is exactly the expected one, so a sender cannot skip a device and a recipient cannot be injected by the sender.
4. The payload carries the group's id as `conversationId`; the receiver binds it to the relay metadata as for one-to-one chats, so the relay cannot replay a ciphertext into another conversation or as another sender.

Blob keys for photos, voice messages and videos travel **inside the payload**, not beside it, so they reach every recipient the same way the text does with no extra mechanism: one blob is uploaded once, one descriptor with its key is sealed per device. The caps (4 MiB photos, 8 MiB voice, 40 MiB video), the upload quotas and the 30 day retention are the one-to-one ones, counted per uploader, not per recipient.

**Cost.** Sending is O(devices of all members): a message in a group of ten people with two phones each is 19 sealed copies, and the first message to a new device also costs a key claim. The relay's per-device and per-sender backlog caps apply per recipient device. This is the price of having no group ratchet; a group of 10 is as large as it gets for this design, and a larger group would need a sender-key design (one symmetric chain per sender, rotated on every membership change), which is a different project.

## Membership changes

The relay holds the roster and enforces who may change it (owner for invites, removals and renames, anyone for leaving). Changes that have other members to tell travel with an encrypted **control message** sent in the same request (`accept`, `leave`, `remove`, `rename`), so there is no moment when the roster and the recipients disagree. Each member's phone applies a received control message in **one commit** with the ratchet that opened it and the notice it shows (the same "history, notice and keys together" rule the pin and new-device notices follow).

- **Removal and leaving are enforced by the phones, not only by the relay.** A `remove` or `leave` message makes every receiving phone keep a *removal mark* for that person (user id and relay time). From then on it does not seal messages for that person's devices, **even if the relay still lists them as a member**. If the relay lists someone the phone holds a mark for, a send is refused with `409 DEVICES_CHANGED` and the app tells the person ("Group membership out of sync: Sam was removed, but the server still lists them. Nothing was sent to them.") instead of sealing for them. An authenticated `join` message from that same person (a genuine re-invite and acceptance) lifts the mark. A removed person's own phone shows "You were removed" and stops sending.
- **Adding is asserted by the relay, but a new person must be accounted for.** A phone keeps, per group, the set of people it has *accounted for*: everyone the relay listed when this phone first saw the group (the creator accounts only for themself, because everyone else joins by an authenticated message), plus everyone whose `join` message it has received, minus the people it holds removal marks for. The relay can list someone who is not in that set only by inventing them, so such a person is shown in Group info as **Not confirmed** (with a **Confirm** action), is not sealed for, and a send that needs them stops with `GROUP_UNCONFIRMED_MEMBER` after the phone polls its inbox once (a `join` that is merely in flight arrives then) and retries. See the review items below.
- **No history for newcomers.** A joiner's phone starts with an empty history for the group and a notice "You joined". Nothing is copied to them; the relay has no copy to give.
- **Account deletion** cannot produce a control message (the person's devices are gone), so the relay records a `member_deleted` event. Phones render it as a notice ("A member deleted their account") and put a removal mark on the id.
- **Owner changes.** When the owner leaves, their `leave` message names the new owner (`owner`); the relay's roster has the same name. A phone that gets an authorisation-sensitive control message (`remove`, `rename`) from someone it does not believe is the owner refreshes the group from the relay once and re-checks.

## Payloads

Plaintext before Olm, padded like every payload (`pad`). The binding fields `v`, `conversationId`, `senderId`, `messageId`, `sentAt` and `text` (always `""` for control kinds) are checked first, as in one-to-one chats. Group messages use the existing kinds (`text`, `image`, `voice`, `video`, `reaction`, `noop`) unchanged, with quotes (`re`) allowed to name any active member of the group as the author (the set of valid `by` values is the group's roster, not "the two people"). The new kind:

```json
{"v":1,"kind":"group","text":"","op":"remove","subject":"<user id>",
 "messageId":"…","conversationId":"<group id>","senderId":"<who did it>","sentAt":"…","pad":"…"}
```

| `op` | Who sends | `subject` | Other fields | Effect on the receiving phone |
|---|---|---|---|---|
| `join` | the person who accepted | must equal `senderId` | none | Notice "Sam joined", lifts a removal mark, adds the name to the local directory. |
| `leave` | the person leaving | must equal `senderId` | `owner`: new owner, only when the leaver was the owner | Notice "Sam left", removal mark for the sender, new owner recorded. |
| `remove` | the owner | the removed member, not the sender | none | Notice "Aditya removed Sam", removal mark. If the subject is this account: "You were removed", the group becomes read-only. |
| `rename` | the owner | none | `name`: 0 to 40 characters, plain text under the usual rules | Notice "Aditya renamed the group to “weekend crew”", new name. |

Receiving rules: the relay's `aux` flag and the decrypted kind must agree (`aux` and kind `group`, or neither), or the message is dropped without a trace; `remove` and `rename` are honoured only from the owner as this phone and the relay know them (after one refresh); `join` and `leave` only when `subject == senderId`; an unknown `op` or a bad `name` is ignored (no notice, no error). A control message never counts as unread and never changes the chat list order.

## What the person sees

- **Chats list.** A **Pending invites** section above the chats: group name (or the people already in it), who invited you, how many are in it, **Accept** and **Decline** (a decline asks for no reason and tells nobody). Groups sit in the same list as one-to-one chats, ordered by activity, with a stack of up to three member photos instead of one photo and a small group mark; they can be pinned (the 5-pin cap is shared), muted and deleted from the list like any chat (30 days to restore). No online dots, no read receipts, no typing.
- **New group.** From the Chats list toolbar. Pick up to 9 people from **Chatting** and **Following** (search, no one else is shown), then an optional name. If the relay says someone cannot be added the app says only that: "Sam can’t be added to this group." Nobody learns why, including the person who asked.
- **Thread.** A header with the member photo stack, the name (or the first names of the members) and the member count; tapping it opens **Group info**. The sender's name sits above every bubble that is not yours (and above the first of a run); a notice chip shows joins, leaves, removals, renames, deleted accounts and "new device" notices. Quotes, reactions (one per member per message), photos, voice and video work as in one-to-one chats. Auto-translate is per group and stays on the phone. A group you were removed from, or that closed, is read-only with a calm line in place of the composer.
- **Group info.** The members (you, the owner mark, everyone else with their photo and name, tapping one opens their profile), pending invites (to members), **Add people** and **Remove** (owner), **Rename** (owner), mute, pin, **Safety number** per member (the existing screen), **Leave group** (the owner is asked who takes over), and a note that messages in this group are end-to-end encrypted with each member's devices. Reporting a group message works from the message menu like in one-to-one chats and shares only the reporter's own decrypted copy.
- **Notifications.** A push for a group message says "New message", never the group name, the sender or any text (the one-to-one rule); muted groups and muted or restricted senders are silent; the push opens the group.
- **Accessibility and layout.** Every control has a label and a 48 dp target; the member stack is decorative and the count is read out; layouts hold at 320 dp wide and with text at 200%; every inset uses start and end, not left and right, so the screens mirror for right-to-left languages.

## Client structure

- `core/chat/chat_groups.dart`: the models (`GroupInfo`, `GroupMember`, `GroupPending`, `GroupInvite`, `GroupEvent`) and the constants (`groupPeer`, the 40 character name, the ten people).
- `core/chat/chat_group_state.dart`: `GroupLocal` and `GroupStore`, the local per-account state under `hiyall.chat.<uid>.groups` inside the sealed snapshot (cached roster, ownership, the directory of names and photos of people who left, removal marks, the accounted-for set, the notice and message ids already filed, read-only and deleted-from-list flags). It is wiped with the rest of the account's chat data (sign-out, deletion, a closed chat's 30 days) and is written in the same commit as the history and the ratchet.
- `core/chat/chat_api.dart`: the group routes.
- `core/chat/chat_engine.dart`: `isGroup`, the group branch of `_deliver` (`_groupSend`: the peer id argument is the empty string, `groupPeer`, and is ignored for a group), `_groupPlan` (who is sealed for), the membership messages (`_applyGroupControl`), `parseIncoming` for kind `group` with the `aux` cross-check, the group as the roster for quote authors, `groupDirectory(groupId)`, the list calls (`groups`, `hiddenGroups`, `groupInvites`, `group`) and the operations (`createGroup`, `inviteToGroup`, `acceptGroupInvite`, `declineGroupInvite`, `renameGroup`, `removeFromGroup`, `leaveGroup`, `confirmGroupMember`). A group the relay no longer lists (removed, left) is served from this phone's record, read-only, until the person deletes it.
- `features/chat_groups_data.dart` (providers, the merged chat list, the wording of each refusal), `chat_groups_list.dart` (member photo stack, group mark, pending invites), `chat_groups_new.dart` (new group and add people, one picker), `chat_groups_thread.dart` (header, read-only line), `chat_groups_info.dart` (Group info), with small group branches in `chat.dart`, `chat_list.dart`, `chat_list_actions.dart`, `chat_header.dart`, `chat_thread.dart`, `chat_menu.dart`, `chat_format.dart`, `chat_reactions_ui.dart` and `safety.dart`.
- Tests: `test/chat_groups_engine_test.dart` (48 tests, 44 of them over three real Olm engines against `test/chat_groups_helpers.dart`'s in-memory relay with the relay's real rules: exact device sets, `DEVICES_CHANGED`, the aux flag on membership messages, invites, events), `test/chat_groups_ui_test.dart` (67 widget tests: invites, rows, the picker, thread, Group info, 320 dp at text scale 2.0, right to left), Go: `internal/httpapi/groups_test.go` and the account purge test world.

Details worth knowing: notices are written from the viewer's side ("You removed Sam", "You joined", "Sam left"); the relay's `created`, `closed` and `owner_changed` events add no notice (a "closed" notice would show that invites were declined); an event and the membership message that carried it share one notice id (`grp-<messageId>`), and state (accounted-for people, removal marks, owner) changes only from an authenticated message, once per message id; events older than the account's own join are skipped; control messages never seal for a marked or unconfirmed person (the one exception: the person being removed is sealed for, so they learn of it), so `leave` or `rename` can stop with the codes below; accepting an invite starts a new membership (marks cleared, accounted-for people are exactly those the join was sealed for); read-only is sticky until the person's own later `join` or a new accept. Failure codes the screens map: `GROUP_WAITING`, `GROUP_UNCONFIRMED_MEMBER` and `GROUP_OUT_OF_SYNC` (409, with `details.userId` and `userIds`), local `CONVERSATION_CLOSED`, `NOT_A_MEMBER` and `VALIDATION` (a name over 40, an owner leaving without a successor, removing yourself), and the relay's codes in [the API note](../api/29-group-chat.md#errors).

## Security notes and review items

What a group does **not** protect, stated plainly:

1. **The relay asserts membership additions.** A malicious or compromised relay can put a person into a group's roster, or a device into a member's account. For *people*, the accounted-for rule above means a phone does not seal for a roster entry that no authenticated `join` message (or this person's own confirmation) explains; that does not help a joiner who relies on the relay's first roster snapshot when accepting an invite (the joiner trusts the inviter's group as the relay describes it), nor a phone that was offline long enough to lose the `join` messages. For *devices* of a known member, the protection is that of one-to-one chats and is partial: a new device on a known account raises the "new device was added" notice in the group (pins are per account, shared with one-to-one chats), the account's own devices are told and pushed when a device is added, and every member has the safety-number screen. **This is the main item for the independent crypto review.**
2. **Removals are enforced by the phones but are only as strong as the control message arriving.** A phone that missed the `remove` (offline for more than the 30 days an envelope lives) falls back to the relay's roster. The relay's `events` list and the `GET /v1/groups/{id}` roster would fix that, and they are also what a malicious relay controls. A removed person keeps every message they already received; nothing can take that back.
3. **No forward secrecy beyond Olm's per-session ratchets and no post-compromise recovery group-wide.** A removed member's phone keeps the Olm sessions it had with the others; the relay never gives it new ciphertext, and the others stop sealing for it, but the sessions themselves are not rotated, because there is no group key to rotate.
4. **Metadata.** The relay knows the roster, roles, group name, invite times, and for every message who sent it, when, how large, and which devices it was sealed for. Message sizes are padded to buckets like one-to-one messages. The relay sees the number of envelopes, so the group size is not a secret from it.
5. **One name for everyone.** The group name is visible to the relay and to members, so it is validated and displayed as user text everywhere it appears (length 40, the usual character rules, never rendered as markup). A name is not a place for content that needs end-to-end secrecy.
6. **A member can still screenshot, forward or report.** Reporting shares the reporter's own decrypted copy, volunteered, as in one-to-one chats; the relay cannot verify it, and the apps cannot stop a member from saying anything about what they saw.
7. **Sealed-for-all fan-out and abuse.** One member can make the relay store up to 100 envelopes per message. The limits above (per-sender daily quota, per-device and per-sender backlog caps, reaction limiter, body size cap of 3 MiB) bound it; see the limits table.

Things for the reviewer to look at first: the control message authorisation rules and the removal-mark logic in `chat_engine.dart`; the `aux`/`kind` cross-check; that no code path seals for a user the phone holds a mark for; that `DEVICES_CHANGED` handling cannot loop; the relay's exact device-set check for groups (`store/groups.go`, `sendGroupMessage`); and whether the missing group-wide key rotation after a removal is acceptable for the product's threat model.
